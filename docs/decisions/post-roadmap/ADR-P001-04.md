# ADR-P001-04 — The fourth SLA clock stays a C021 measurement definition; small-sample floor ratified

- **Status:** Proposed (binds downstream dispatch only after TL harvest/merge)
- **Work order:** P001 (issue #153) · **Register rows:** R-079, R-080, R-050
- **Binds:** P002 (wiring), P006 (SLA acceptance flows), P005 (ops board truth states)

## Context

C011 (PR #141) delivered a three-clock SLA contract:
`SLA_CLOCK_KINDS = ['accept', 'start', 'submit']` in a **versioned** `SlaPolicy`
(windows by urgency class). C021 (PR #150) delivered SLA **measurement** over a
four-clock `SlaMeasurementDefinition` — C011's three plus **validate-by** — with a
recorded DEVIATION NOTE in `packages/escalation-observability/src/sla.ts`: validate-by
is not in C011 policies; it "defaults to the SAME class's accept window". PR #150 asked:
"should the fourth SLA clock become a C011 policy concern (extended `SlaPolicy`) or stay
a C021 measurement definition with the derived default? Currently the latter; the default
needs ratification." It also asked whether `DEFAULT_SMALL_SAMPLE_MIN = 5` should be
ratified as the platform default or made tenant-configurable.

## Decision

1. **Validate-by stays a C021 measurement definition.** C011's `SlaPolicy` keeps exactly
   three clock kinds — the policy authority (what windows the platform promises) is not
   changed by a measurement surface. C021 derives validate-by as
   `submittedAt + the same urgency class's accept window`, exactly as its disclosed
   deviation note specifies. This preserves lock rule 16: C011 owns SLA policy +
   arithmetic; C021 owns measurement, evidence law and supersession.
2. **The derived default is ratified** as the platform measurement default (versioned in
   the `SlaMeasurementDefinition`, which already carries a version for exactly this).
3. **`DEFAULT_SMALL_SAMPLE_MIN = 5` is ratified as the platform default.** Cross-tenant
   SLO aggregates continue to SUPPRESS detail below the floor. Tenant-configurable floors
   via the ops surface are a follow-up (TL backlog), not a P-series requirement.
4. If product later wants validate-by to be a *promised* window (policy), that is a
   versioned `SlaPolicy` bump in C011 coordinated with an ACR-level review — explicitly
   NOT part of this ADR.

## Alternatives considered

1. **Extend C011's `SlaPolicy` to four clocks** — rejected for P-series: it changes a
   merged, versioned domain contract mid-program, forces C011/C021 dual migration, and
   blurs the policy/measurement authority line the lock protects.
2. **Drop validate-by from C021** — rejected: ES1.0 validation is a lifecycle step;
   measuring it is required by the observability work order and already shipped with an
   evidence law (`met` records require milestone time + backing event ids).

## Consequences

- No C011 code or contract change; C021's shipped measurement stands as canonical.
- P002 wires the C011 clock feed into C021 measurement unchanged; P006 asserts
  met/pending/at-risk/breached outcomes with reasons + supersessions.
- The ratified defaults are versioned constants — a future bump is a deliberate,
  reviewable change, not silent drift.
- No Architecture Lock change.
