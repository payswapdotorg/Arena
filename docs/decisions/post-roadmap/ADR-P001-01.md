# ADR-P001-01 — One shared durable job runner at the host boundary

- **Status:** Proposed (binds downstream dispatch only after TL harvest/merge)
- **Work order:** P001 (issue #153) · **Register rows:** R-073, R-022, R-035, R-043, R-049, R-082
- **Binds:** P002 (owner), P006 (restart/recovery acceptance), P003 (job-driven webhook dispatch)

## Context

C-series services (C004, C012, C015, C016, C020, C021 among them) each implemented
"durable idempotent jobs" over in-memory reference fabrics with per-service job loops.
PR #148 (C016) asked directly: "Should durable recompute jobs later move to a shared job
runner (e.g., C011-adjacent infra) instead of per-service persistence?" Related scheduling
questions: PR #134 Q3 (timeout ownership), PR #137 Q3 (who schedules requalification),
PR #139 Q3 (retention sweep scheduling), PR #141 Q2 (availability refresh), PR #150 Q4
(event-fed vs scheduler-driven projection feeding). The repo already owns the protocol and
engine: `packages/job-protocol` (A015 — versioned `JobDefinition`, append-only `JobRecord`,
idempotency identity, retry/timeout policy as pure data, tamper-evident audit chain) and
`services/job-orchestrator` (deterministic state machine over injected `JobStore` /
`EventSink` / `Clock` ports).

## Decision

P002 builds **one shared durable job runner** at the host boundary
(`services/runtime-host` + `packages/runtime-host`), composed from
`services/job-orchestrator` over `@arena/job-protocol`, with a **single durable
`JobStore`/`EventSink` adapter** over the Neon/Postgres persistence surface. Every
C-series service's job kinds (recompute, requalification, retention sweep, projection
materialization, learning pipeline, dispute/COI jobs) are registered as
`JobDefinition`s executed through this runner. Services keep their domain idempotency
contracts (required idempotency keys; replays return recorded outcomes verbatim) — the
runner provides durability, claiming, retry/backoff, timeout and recovery, not domain
outcome judgment.

Feeding model (resolves R-082): **both** — event-fed subscription (C001 lifecycle events,
trigger events per R-036) submits materialization jobs; a scheduler-driven sweep of due
jobs backstops. Timeouts and cadence are declared as pure data on definitions
(R-022/R-035/R-043); the runner never sleeps and reads only the injected clock
(A015 law, lock rule 17).

## Alternatives considered

1. **Per-service private persistence/loops** (each service runs and stores its own jobs) —
   rejected: duplicates recovery/idempotency logic across ~10 services, divergent restart
   semantics, and P002's acceptance ("restart resumes without loss or duplicate
   transition") would have to be proven N times.
2. **C011-adjacent infra** (engagement service owns scheduling for everyone) — rejected:
   violates lock rule 16 (one responsibility, one authority); engagement is a domain, not
   platform infrastructure.
3. **In-memory fabrics promoted to runtime** — rejected: reference fabrics are test/demo
   fixtures by house design (handoff §1.1); the production path must be durable.

## Consequences

- P002 owns job-table migrations, claiming semantics, poison/dead-letter handling and the
  restart/recovery proof for ALL registered job kinds in one place.
- C-series in-memory job fabrics remain as test fixtures; no domain package changes are
  required (their idempotency contracts already fit the A015 identity model).
- The A015 audit chain applies uniformly to consequential job mutations at the host.
- Risk accepted: the runner becomes a single point of failure — mitigated by durable
  records + idempotent replay (a restarted runner resumes from the store, never
  re-executes a terminal job).
- No Architecture Lock change (rule 17 already mandates idempotent, correlation-addressable
  jobs; this ADR operationalizes it).
