# ADR-P001-02 — The explicit Demo/customer truth lens is the canonical read-model convention

- **Status:** Proposed (binds downstream dispatch only after TL harvest/merge)
- **Work order:** P001 (issue #153) · **Register row:** R-074
- **Binds:** P002, P003, P005, P006 (all read/query surfaces and acceptance evidence)

## Context

C016 (PR #148) asked: "Is the EXPLICIT truth lens (demo vs customer economics) the
canonical pattern for other read-model services to adopt?" The repo already carries the
law — `docs/architecture-lock.md` A2.0: "Demo state is not customer state" — and several
surfaces implement it piecemeal: C016's read models take an explicit lens; C017's portal
labels live vs sandbox truth per row; C021's board uses a reserved labelled demo tenant;
the demo twins under `/demo/**` are visibly labelled. Without a canonical convention,
productionization could blend demo fixtures into customer reads (or vice versa) at the
host boundary.

## Decision

**Yes — adopt it canonically.** Every service query/read surface exposed through the
production host takes an **explicit truth-lens parameter** (or an explicitly labelled
projection state) with exactly two values: `demo` and `customer`. Rules:

1. Demo data is deterministically seeded, visibly labelled in every projection payload
   and rendered UI, and never blended with customer records.
2. Persisted records carry the lens they were produced under; cross-lens reads fail
   closed rather than silently merging.
3. The reserved demo tenant composition is the ONLY path that resolves `demo`; live
   tenant sessions resolve `customer` (C021's fail-closed session-boundary pattern).
4. Acceptance evidence (P006) must state the lens under which every observation was made.

## Alternatives considered

1. **Per-service ad-hoc conventions** — rejected: the C-series already drifted in naming
   (truth labels vs demo corpus vs role lens); one convention prevents silent blending at
   the composition root.
2. **Separate demo deployment** — rejected for the P-series: zero-credential demo is a
   product requirement (P004 acceptance: "Demo still runs with zero provider
   credentials"), so the lens must live inside one host.

## Consequences

- P002 persists the lens on lifecycle/event/job records; P003 exposes it consistently on
  HTTP/MCP reads; P005 preserves truth-state vocabulary on mounted routes; P006's
  evidence records it.
- Slight API surface cost: one more required field on read queries — accepted for the
  honesty guarantee.
- No lock change: this operationalizes the existing "Demo state is not customer state" rule.
